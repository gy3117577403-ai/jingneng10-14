# 京能协同平台 · 应用接入规范

> 面向后端实现者（Codex）与后续应用开发者。目标：新应用（图纸快速分解、快速报价、…）**不改平台代码**即可接入。
> 平台 = 壳（登录/菜单/权限/通知/附件/审批/日志）+ 应用（各业务模块）。

---

## 一、平台架构

```
┌────────────── 京能协同平台 ──────────────┐
│ 平台壳（稳定，不随应用增加而改）            │
│  登录鉴权 / apps应用注册表 / 权限校验        │
│  通用审批流 / 通知 / 附件 / 操作日志        │
├──────────────────────────────────────────┤
│ 应用A：报价管理   应用B：价格库   应用C…    │
│ (code=quote)    (code=price)   (code=xxx) │
└──────────────────────────────────────────┘
```

- **前端**：侧边栏菜单从 `GET /api/apps`（仅 status=1，按 sort 排序）动态渲染；路由 `#/app/{code}/…`。
- **后端**：按应用划分 API 前缀 `/api/{code}/…`；公共能力放在 `/api/common/…`。

## 二、新应用接入五步

以"图纸快速分解"（code=`drawing`）为例：

### 步骤1：注册应用

```sql
INSERT INTO apps (code, name, icon, route, sort, status)
VALUES ('drawing', '图纸分解', 'scan', '/app/drawing', 30, 1);
-- 先 status=0 开发联调，上线时改为 1 即出现在菜单
```

### 步骤2：注册权限点

```sql
INSERT INTO app_permissions (app_id, perm_code, perm_name) VALUES
  ((SELECT id FROM apps WHERE code='drawing'), 'drawing:view', '查看图纸任务'),
  ((SELECT id FROM apps WHERE code='drawing'), 'drawing:create', '新建分解任务'),
  ((SELECT id FROM apps WHERE code='drawing'), 'drawing:approve', '审核分解结果');
```

### 步骤3：建业务表（命名规范）

- 新表必须以 `app_{code}_` 为前缀，如 `app_drawing_tasks`、`app_drawing_parts`。
- 实体表沿用平台约定：`id` BIGINT UNSIGNED 自增主键、`created_at`/`updated_at`、`deleted_at` 逻辑删除、中文 COMMENT。
- 需要走审批的业务表，建议加 `approval_status` 字段（枚举同 quotes.approval_status）。

### 步骤4：前端页面

- 路由挂载到 `#/app/drawing/…`（如 `#/app/drawing/list`、`#/app/drawing/detail/:id`）。
- 复用平台组件：详情抽屉、审批时间线、评论区、附件上传（见第四节）。

### 步骤5：联调清单

- [ ] 菜单出现且可伸缩侧边栏正常
- [ ] 无权限用户访问被拦截（403 + 友好提示）
- [ ] 审批流：提交→通知→通过/驳回→状态回写
- [ ] 操作日志有记录
- [ ] 附件上传/下载正常

## 三、命名与路由约定

| 约定项 | 规则 | 示例 |
|---|---|---|
| 应用编码 | 小写英文，全局唯一 | `drawing` |
| 新表前缀 | `app_{code}_` | `app_drawing_tasks` |
| API 前缀 | `/api/{code}/…` | `POST /api/drawing/tasks` |
| 前端路由 | `/app/{code}/…` | `/app/drawing/detail/12` |
| 审批业务类型 | `biz_type = 'app_{code}'` 或简写 | `app_drawing` |
| 附件业务类型 | `biz_type = 'app_{code}'` | `app_drawing` |
| 通知跳转链接 | `/app/{code}/detail/{id}` | `/app/drawing/detail/12` |
| 权限编码 | `{code}:{action}` | `drawing:approve` |

## 四、必须复用的公共能力

| 能力 | 表/接口约定 | 调用方式 |
|---|---|---|
| 登录鉴权 | 后端签发 Token（建议 JWT，有效期 8h） | 请求头 `Authorization: Bearer <token>`；前端 401 跳登录 |
| 权限校验 | `app_permissions` + 用户角色 | 每个业务接口校验 `perm_code`；前端按权限隐藏按钮（以后端校验为准） |
| 审批流 | `approvals` + `approval_records` | 新建业务单据提交时：`INSERT approvals(biz_type='app_drawing', biz_id=…)` + 首条 `approval_records(action='submit')`；审批动作只允许 `approve/reject/return/cancel`，并同步回写业务表状态 |
| 通知 | `notifications` | 审批提交→通知下一节点人（type=approval）；@人→通知被@人（type=mention）；`link_url` 按第三节约定 |
| 附件 | `attachments` | 上传→对象存储→`INSERT attachments(biz_type='app_drawing', biz_id=…)`；下载走后端鉴权代理，不暴露直链 |
| 操作日志 | `operation_logs` | 增删改、提交、审批、调价等动作必须写；`module='{code}'` |
| 单号生成 | 见数据字典第二章 | 各应用单据号各自加前缀（如图纸任务 `T`+YYYYMM+流水），取号方式统一用序列表/Redis |

**禁止事项**：新应用不得自建用户体系、不得自建审批表、不得绕过权限校验直连业务表。

## 五、菜单与权限点注册方式

1. **菜单**：只读 `apps` 表。`status=1` 显示，`sort` 排序。应用下线/灰度：改 `status` 即可，无需发版。
2. **权限点**：只增不改。`perm_code` 一旦被角色引用，不得修改或删除（只能停用）。
3. **角色绑定**（建议）：新建 `role_permissions(role_id, perm_id)` 表；本期过渡方案可在后端配置 `ROLE_PERMS = {'salesman': ['quote:view','quote:create',…]}` 常量，后续表化。

## 六、API 设计建议（推荐，不强制）

- REST 风格，统一分页：`GET /api/quote/quotes?page=1&pageSize=20` → `{ code:0, msg:'ok', data:{ list:[], total:0 } }`
- 错误码：`code!=0` 为业务异常（如 `40001`=无权限，`40002`=状态不允许）；`msg` 给人看的中文。
- 列表接口默认过滤 `deleted_at IS NULL`，默认按 `created_at DESC`。
- 金额字段以"元"为单位，小数点后两位；数量最多三位小数。
